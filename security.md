# Security architecture and production hardening

This document describes the security controls configured by this repository for its Amazon EKS-based LLM inference service, and the work needed to harden a production deployment. It is a review of the infrastructure code and accompanying documentation, not an audit of a deployed AWS account. Account-level policies and controls may exist outside this repository and should be verified in the target environment.

The deployment runs NVIDIA Triton with a vLLM backend on GPU workers in private subnets. It uses two separate internal Application Load Balancers (ALBs): one for the inference API and one for Grafana. Model archives are downloaded from JFrog Artifactory to shared Amazon EFS storage. Operators can use AWS Systems Manager (SSM) Session Manager for node diagnostics. The implementation is a starting point; private networking alone does not establish identity or protect every internal connection.

## Connection and trust boundaries

| Connection | Current implementation | Main limitation |
|---|---|---|
| Client → inference ALB | Internal ALB, configured trusted source CIDRs, HTTPS using an ACM certificate, and TLS 1.2 or newer. A private Route 53 record points to the ALB. | Private network access and a shared bearer key do not provide individual identity or fine-grained authorization. |
| Inference ALB → gateway → Triton | The gateway checks the bearer key, strips it before forwarding, and returns 401 for a missing or invalid key. Kubernetes network policy restricts Triton API ingress to gateway-labeled pods and metrics ingress to Prometheus-labeled pods. | Both internal hops use HTTP. Policy has a possible startup enforcement window and does not isolate privileged node processes, cluster administrators, or authorized port-forward users. |
| Client → Grafana ALB | A separate internal ALB uses configured source CIDRs. Grafana requires login and receives an initial admin password through Terraform. | The listener is HTTP, so credentials and traffic are not encrypted on that connection. Operators must choose narrow, trusted CIDRs. |
| Triton init container → JFrog | Direct HTTPS archive URLs, TLS certificate validation, and a bearer token read from a Kubernetes Secret. An optional private CA certificate can be supplied. | The token is also in Terraform state. The download process does not verify archive checksums or signatures. |
| Operator → GPU node | IAM-authorized SSM Session Manager; node roles include `AmazonSSMManagedInstanceCore`. This stack does not open inbound SSH or distribute SSH keys. Private nodes reach SSM through NAT. | Operator permissions and session logging must be configured and verified separately. |

The inference ALB terminates TLS. The gateway and Triton communicate over the cluster network without application-layer TLS. The public Route 53 parent zone is used for ACM DNS validation; the inference endpoint itself uses private DNS. See [inference.md](inference.md) for the full request path, DNS setup, key rotation and network-policy boundaries. Grafana is reached over a VPN or another private route from a permitted source range; the starter HTTP listener should be replaced with HTTPS for production.

## Systems Manager access

SSM is a management path to EC2 worker nodes. It is not the connection or authentication mechanism for either ALB or JFrog. An operator with appropriate IAM permissions and the Session Manager plugin can start a shell on a GPU worker without exposing SSH. The optional SSM State Manager association can also install and maintain the host DCGM CLI and engine; it is enabled only when configured. See [operation.md](operation.md#secure-gpu-worker-shell-optional) for operational instructions.

Session activity and session contents have different audit requirements. AWS supports recording Session Manager API activity in CloudTrail. Recording shell input and output to CloudWatch Logs or S3 requires appropriate session preferences, destinations and permissions; this repository does not establish that account-level settings are enabled. Session-content logging is unavailable for Session Manager port-forwarding or SSH sessions. Protect logs because shell output may contain sensitive data. See [AWS session activity logging](https://docs.aws.amazon.com/systems-manager/latest/userguide/session-manager-auditing.html) and [session logging](https://docs.aws.amazon.com/systems-manager/latest/userguide/session-manager-logging.html).

## Other controls in the repository

- **Network and cluster access:** Workers use private subnets. The EKS API has private access enabled and also has a public endpoint restricted by `admin_cidr_blocks`; those CIDRs must be chosen carefully. VPC CNI network-policy support is enabled. The Triton policy is label-based, so permission to create pods or apply trusted labels is security-sensitive.
- **IAM:** The EFS CSI driver, AWS Load Balancer Controller and Karpenter use IAM roles for service accounts. Nodes have separate IAM roles, including SSM permissions. Review policies and trust relationships in the target account rather than assuming all granted actions are minimal.
- **Encryption at rest:** EFS, Karpenter GPU node root volumes and the Karpenter interruption queue are configured for encryption. Amazon EKS provides default envelope encryption of Kubernetes API data on clusters running Kubernetes 1.28 or later; using a customer-managed KMS key is a separate decision. See [AWS EKS encryption documentation](https://docs.aws.amazon.com/eks/latest/userguide/envelope-encryption.html). Encryption at rest does not prevent authorized API users from reading Secrets.
- **Instance metadata:** The Karpenter GPU NodeClass requires IMDSv2 and sets the metadata response hop limit to one. Review equivalent settings for any other node groups and test workload credential isolation.
- **Gateway container:** The gateway image is pinned by digest, runs without root, has a read-only root filesystem, and drops Linux capabilities. Its access logs omit bearer keys, request bodies and query strings. `/healthz` is an unauthenticated health check; other non-API routes, including `/metrics`, return 404.
- **Secrets:** The JFrog token and inference keys are Kubernetes Secrets rather than ConfigMaps. Terraform marks sensitive inputs as sensitive, and the repository ignores tfvars and state files. Multiple inference keys support overlapping rotation. These controls do not keep the secret values out of Terraform state or saved plans.
- **Audit visibility:** EKS control-plane API, audit, authenticator, controller-manager and scheduler logs are enabled. The repository does not configure a centralized Triton application-log pipeline. Verify retention, access and alerting in the deployment.
- **Profiling privileges:** Alloy is scheduled on GPU-labeled nodes and selects Triton processes, but runs privileged as root with host PID access for eBPF. Treat this as significant node-level access. The DCGM exporter also requires elevated capabilities for configured profiling counters.

## Production hardening priorities

1. **Encrypt connections.** Add an HTTPS listener and suitable certificate to the Grafana ALB. Assess TLS or mutual TLS for ALB-to-gateway and gateway-to-Triton traffic, and verify EFS mount transport security against organizational requirements. Use proper hostname and CA validation; do not solve certificate issues by disabling verification.
2. **Strengthen identity and authorization.** Integrate Grafana with organizational SSO, MFA and role-based access, and limit routine use of the shared admin account. Replace or supplement shared inference keys with user or workload identities, scoped authorization, quotas and rate limits. Restrict Kubernetes RBAC, especially Secrets, pod creation, trusted labels, `exec` and port forwarding.
3. **Reduce secret exposure.** Use encrypted remote Terraform state with locking, narrowly scoped IAM and KMS access, and protected state backups and CI artifacts. Consider a managed secret store and delivery mechanism that avoids putting long-lived values through Terraform state. Establish rotation and revocation procedures for JFrog, inference, Grafana and registry credentials. Handle saved plans as sensitive.
4. **Harden and audit SSM.** Scope `ssm:StartSession` to approved operators, instances and session documents; use temporary identity credentials and MFA. Explicitly configure and test CloudTrail, encrypted session logs, retention, access controls and alerts. Consider private VPC endpoints for Systems Manager and related services rather than relying solely on NAT.
5. **Tighten network boundaries.** Restrict ALB and EKS API CIDRs to actual trusted sources; consider private-only EKS API access when operationally practical. Review security groups, EFS access and outbound access to JFrog and registries. Add and test appropriate ingress and egress policies, including DNS and required system dependencies before enabling stricter enforcement.
6. **Protect the supply chain.** Use immutable model versions and verify checksums or signatures before extraction. Scope the JFrog token to read-only access to required artifacts. Scan, patch and review container images, dependencies and node AMIs. The EFS completion marker does not verify integrity or detect an archive changed at the same URL; coordinate cache refresh as documented in [operation.md](operation.md#switch-the-active-model).
7. **Improve detection and recovery.** Centralize and protect gateway, Kubernetes, AWS and application security logs. Set retention and alerts for authentication failures, unusual SSM activity, secret access and configuration changes. Define and test backups and recovery for EFS, Terraform state and observability data, alongside incident response and credential revocation.
8. **Review privileged components.** Assess Alloy's host access and DCGM exporter privileges against the threat model. Restrict who can modify their workloads, service accounts and images, and test least-privilege configurations where supported.

Before relying on these controls, verify the deployed ALB listeners and CIDRs, EKS endpoint access, network-policy enforcement, IAM permissions, SSM audit configuration, secret storage and logging with the relevant security and operations teams. The verification and limitations for the inference path are described in [inference.md](inference.md#verification-and-troubleshooting).
